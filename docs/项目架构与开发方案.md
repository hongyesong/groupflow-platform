# GroupFlow 最小 MVP 架构

本方案依据 `kapibala项目-2026-09-26.md`，按用户要求采用简单实现和原生部署。原文没有要求 Docker，本项目不使用 Docker、Redis 或独立消息队列。

## 系统组成

```text
React 18 控制台
      │ HTTP API + WebSocket
Node.js + TypeScript（一个进程）
      ├─ 登录、账号、群、消息、序列、Agent
      ├─ 后台循环：扫描持久化任务并继续执行
      ├─ HTTP/SSE 消息网关模拟器（仅本机）
      └─ HTTP Agent 模拟器（仅本机）
      │ PostgreSQL 原生连接
PostgreSQL（仅本机）
```

前端通过 HTTP API 访问业务数据，不直接访问数据库。部署使用 Node.js + PostgreSQL + systemd。已有的其他项目和数据库不修改。

## 要做的功能

| 功能     | 实现                                                   |
| -------- | ------------------------------------------------------ |
| 登录     | admin/viewer、access token、refresh cookie、轮换和撤销 |
| 账号     | 状态机、CAS、限流、停用后的联动                        |
| 群       | 建群、邀请、入群确认、提权、群主最后退群               |
| 消息     | 持久排队、投递状态、去重、超时结果核对、分页           |
| Agent    | 四个工具、审计、幂等、运行预算、步骤记录               |
| 序列     | 角色选人、变量预检与来源、按前一步发出排期             |
| 实时通知 | WebSocket seq、持久事件、重连补发                      |
| 模拟器   | 可演示正常流程、重复事件、限流、超时等场景             |

媒体文件和真实 LLM 为原文选做项，首版不实现。

## 用户问到的数据库机制

| 名称                           | 原文是否要求                             | 本项目做法                              |
| ------------------------------ | ---------------------------------------- | --------------------------------------- |
| seq                            | 明确要求 WS 事件全局单调递增             | 事务计数器 + realtime_events            |
| 幂等                           | 明确要求消息和 Agent 相同 key 不重复执行 | 唯一索引、发送记录与结果核对            |
| 对话限时                       | 明确要求 12 步、60 秒、单轮 10–15 秒     | step_count、elapsed_ms、请求超时        |
| lease                          | 未要求                                   | 不设 lease 表，采用数据库 advisory lock |
| LIMIT / FOR UPDATE SKIP LOCKED | 未指定                                   | 仅在需要竞争领取数据时采用              |
| 独立消息队列                   | 未要求                                   | PostgreSQL 保存业务待处理状态           |
| Docker                         | 未要求                                   | 不使用，改为原生安装和 systemd          |

数据库锁只保证执行互斥，不能证明外部 HTTP 请求没有执行。消息结果不明时先核对，不盲目重发。

## 数据结构

- users、sessions、tokens：用户与会话。
- accounts、groups、group_members、pending_disconnects：账号和群。
- jobs：建群、退群进度。
- messages：投递状态和发送尝试。
- gateway_inbox：网关事件去重与重放。
- event_counter、realtime_events：前端实时通知。
- agent_runs、agent_steps、agent_pending_messages、agent_send_keys：Agent 执行。
- sequences、sequence_runs、sequence_run_steps：定时序列。
- timeline_snapshots：稳定分页。
- mock_state、mock_events、mock_tasks：模拟器持久状态。

表结构见 `server/schema.sql`。不要求表名或所有主键都叫 seq。

## 可靠性与协议边界

原文要求任意时刻重启后保持业务行为，但部分外部接口没有给出足够的恢复条件：

1. 建群成功而响应丢失时，原接口没有请求幂等键或查询接口。模拟器补充可选 requestId；真实服务需要同等能力。
2. 发消息后进程退出，若没有收到 504，原文没有明确该请求的最长处理时间。无法证明未发送时保留 unknown；不靠重试假装实现 exactly-once。
3. 同一 Agent turn 重放需要稳定响应。模拟器按 runId 和会话历史决定结果；真实服务需要明确重放语义。
4. promote 成功但保存前崩溃，需要允许幂等重复调用或查询成员角色；原成员查询不含角色。
5. leave-all 只退出服务账号，因此 API members 表示受管服务账号，外部用户另外保存在成员表中。

首版重点保证可运行、关键路径清晰，未声称所有外部故障组合均已完成验收。
